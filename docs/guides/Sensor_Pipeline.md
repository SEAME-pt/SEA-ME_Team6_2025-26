# From Wire to Dashboard — Complete Sensor Pipeline
 
**SEA:ME Project | Team 6**
 
This document explains the complete data flow from a physical sensor to its use in software.
It uses the SRF08 (ultrasonic distance sensor) as the main example, but the pattern applies to
any sensor in the system.
 
After reading this document, any team member should be able to:
- Understand how data flows from the sensor to the dashboard
- Add a new sensor to the system following the same pattern
- Consume existing sensor data via CAN bus for HMI, datalogger, or scripts
 
> **Architecture status (March 2026):** The STM32 → CAN pipeline is fully implemented.
> The Kuksa/VSS layer (sections 5 and 6) is planned but **not yet implemented** in this codebase —
> the current integration boundary is the CAN bus on the RPi5.

## 2. Hardware — Connection Topologies
 
This section covers the three ways to connect a sensor to the STM32 B-U585I-IOT02A.
 
### 2.1 External Sensor via I2C (Main Example: SRF08)
 
#### What is I2C (30-second summary)
 
I2C is a serial communication protocol that uses only two wires:
- **SDA** (Serial Data) — bidirectional data
- **SCL** (Serial Clock) — clock generated by the master (STM32)
 
Each device on the bus has a **unique address** (7 bits). The STM32 (master) initiates
communication by saying "I want to talk to the device at address 0x70", and only that device
responds. This allows multiple sensors on the same pair of wires.
 
#### SRF08 physical wiring

  <img width="1024" height="371" alt="image" src="https://github.com/user-attachments/assets/ced7988e-09f1-45c8-83ae-d129d1d5af35" />



> ⚠️ **Bus note:** The SRF08 is on **I2C1** (hi2c1), shared with the INA226 (0x40)
> and the Grove TB6612FNG motor driver (0x28). Onboard sensors (IMU, pressure, light) are on
> **I2C2** (PH4/PH5). All I2C1 accesses are protected by `ctx->i2c1_mutex` (ThreadX).
 
**Important notes:**
- The SRF08 operates at **5V** but the I2C lines are 3.3V tolerant — it works connected directly
  to the STM32 (3.3V logic) without a level shifter
- Factory I2C address (7-bit): **0x70** → in the ST HAL, use the 8-bit address: **`0xE0`**
  (= `0x70 << 1`). The HAL expects the address in `addr[7:1]` format, i.e., shifted left.
  In code: `#define SRF08_DEFAULT_ADDR 0xE0`
- The SRF08 also has a light sensor (register 0x01) — free bonus
- Pull-ups on SDA and SCL: the SRF08 includes internal pull-ups; if you have communication
  issues, check with an oscilloscope
 
#### Confirming the sensor is connected (I2C scan)
 
The following pattern, extracted from `task_srf08_init()`, confirms the sensor's presence:
 
```c
// Check if the device responds at address 0xE0
tx_mutex_get(&ctx->i2c1_mutex, TX_WAIT_FOREVER);
HAL_StatusTypeDef st = HAL_I2C_IsDeviceReady(&hi2c1, SRF08_DEFAULT_ADDR, 3, 100);
tx_mutex_put(&ctx->i2c1_mutex);
 
if (st != HAL_OK) {
    sys_log(ctx, "[SRF08] IsDeviceReady FAIL st=%d", st);
    return;
}
// Expected result: st == HAL_OK → "Device found at 0xE0 (7-bit: 0x70)"
```
 
For a full I2C scan (debug), the project has the `I2C_Scan(&hi2c2, "I2C2")` function,
callable with `#define ENABLE_I2C_SCAN 1` in `task_environment.c`.
 
### 2.2 External Sensor via SPI
 
#### What is SPI (30-second summary)
 
SPI is another serial protocol, faster than I2C. It uses 4 wires:
- **MOSI** (Master Out, Slave In) — data from STM32 to device
- **MISO** (Master In, Slave Out) — data from device to STM32
- **SCK** (Serial Clock) — clock generated by the master
- **CS/SS** (Chip Select) — the STM32 drives LOW to select which device to talk to
 
Practical differences from I2C:
- **No addresses** — instead, each device has its own CS wire
- **Full-duplex** — sends and receives data simultaneously
- **Faster** — but uses more pins
 
#### Project example: MCP2515 (CAN Controller)
 
The system's CAN controller is an MCP2515 (not MCP2518FD), connected via SPI1:

  <img width="1024" height="371" alt="image" src="https://github.com/user-attachments/assets/571ac988-ddfc-4d56-a0f5-836eb7090716" />



SPI1 configuration in code (`spi.c`):
- Mode: MASTER, 2LINES, 8-bit, CPOL=LOW, CPHA=1EDGE (SPI Mode 0)
- NSS: Software (CS controlled manually via GPIO)
- BaudRate: SYSCLK/16
- FirstBit: MSB
 
**Key differences vs I2C:**
- In code: `HAL_SPI_Transmit()` / `HAL_SPI_Receive()` instead of `HAL_I2C_Mem_Read/Write()`
- CS is controlled manually: `MCP_CS_L()` / `MCP_CS_H()` before/after each transaction
- Protected by `ctx->spi1_mutex`
- **The rest of the pipeline (pack → CAN → consume) is exactly the same**
 
### 2.3 Onboard Sensors on the B-U585I-IOT02A
 
#### What's already on the board
 
The B-U585I-IOT02A includes several integrated sensors — all on I2C2 (PH4=SCL, PH5=SDA):
 
| Sensor | Function | HAL Addr (8-bit) | 7-bit Addr | CAN ID |
|--------|----------|------------------|------------|--------|
| **ISM330DHCX** | Accelerometer + Gyroscope | 0xD6 (0x6B << 1, SDO=VCC) | 0x6B | 0x400/0x401 |
| **IIS2MDC** | Magnetometer | 0x3C | 0x1E | 0x402 |
| **LPS22HH** | Barometric pressure + Temperature | 0xBA (0x5D << 1) | 0x5D | 0x420 |
| **HTS221** | Temperature + Humidity | 0xBE | 0x5F | 0x420 |
| **VEML6030** | Ambient light (lux) | 0x20 (0x10 << 1) | 0x10 | 0x420 |
| **VL53L5CX** | ToF 8×8 (multi-zone distance) | 0x52 | 0x29 | 0x422 |
 
> Note: The STTS22H (high-precision temperature) is not implemented in this codebase.
> The ambient light sensor is the VEML6030, whose value is included in the Environment_t frame (0x420).
 
#### Differences from external sensors
 
The physical wiring is already done on the PCB. The software approach is direct HAL in all cases:
`HAL_I2C_Mem_Read(&hi2c2, addr, reg, ...)` — same pattern as external sensors, different bus.
 
Implemented drivers:
- `ism330dhcx.c/h` — accelerometer + gyroscope via hi2c2
- `iis2mdc.c/h` — magnetometer via hi2c2
- `lps22hh.c/h` — pressure + temperature via hi2c2
- `hts221.c/h` — humidity via hi2c2
- `veml6030.c/h` — ambient light via hi2c2
- `vl53l5cx_driver.c/h` + ULD library — ToF via hi2c2, interrupt-driven
 
The rest of the pipeline is the same: read → pack CAN → send → consume.

## 3. STM32 — Detecting and Reading the Sensor
 
This section uses the SRF08 as a complete walkthrough.
 
### 3.1 CubeMX Configuration
 
I2C1 (for SRF08, INA226, motor driver):
1. Peripheral: I2C1
2. Pins: PB8 → I2C1_SCL, PB9 → I2C1_SDA
3. Speed: Standard Mode (timing 0x30909DEC in code)
4. Analog filter: ENABLE, Digital filter: 0
5. Verify that GPIOB and I2C1 clocks are active (auto-generated by CubeMX)
 
> The SRF08 does not support Fast Mode (400kHz). Standard Mode (100kHz) is mandatory.
 
### 3.2 I2C Scan — Confirming Detection
 
Use `HAL_I2C_IsDeviceReady()` to confirm the sensor is on the bus:
 
```c
// Always protect with mutex in a ThreadX environment
tx_mutex_get(&ctx->i2c1_mutex, TX_WAIT_FOREVER);
HAL_StatusTypeDef st = HAL_I2C_IsDeviceReady(&hi2c1, SRF08_DEFAULT_ADDR, 3, 100);
//                                                    ^^^^^^^^^^^^^^^^
//                                                    0xE0 (= 0x70 << 1)
tx_mutex_put(&ctx->i2c1_mutex);
 
if (st == HAL_OK) {
    // Sensor found at 0x70 (7-bit) / 0xE0 (HAL)
} else {
    // Check physical wiring, pull-ups, 5V power supply
}
```
 
For a full scan (debug), the project includes `I2C_Scan(&hi2c1, "I2C1")` —
enable with `#define ENABLE_I2C_SCAN 1`.
 
### 3.3 How the SRF08 Works
 
The SRF08 measures distance via ultrasound in two steps:
 
1. **Trigger:** Write `0x51` (ranging in cm) to register 0x00
2. **Wait:** The sensor emits an ultrasonic pulse and measures the echo time (~65ms max)
3. **Read:** The distance in cm is in registers 0x02 (high byte) and 0x03 (low byte) as uint16
 
```
SRF08 Registers:
┌──────────┬──────────┬───────────────────────────────────────┐
│ Register │ Access   │ Contents                              │
├──────────┼──────────┼───────────────────────────────────────┤
│ 0x00     │ W / R    │ Write: command | Read: SW version     │
│ 0x01     │ W / R    │ Write: gain (0–31) | Read: light      │
│ 0x02     │ W / R    │ Write: max range | Read: distance Hi  │
│ 0x03     │ R        │ Read: distance low byte (Lo)          │
└──────────┴──────────┴───────────────────────────────────────┘
 
Distance (cm) = (reg_0x02 << 8) | reg_0x03
Physical range: 3 cm (dead zone) — 600 cm (~6m with range=140)
CAN frame conversion: distance_mm = distance_cm * 10
```
 
Parameters used in the project (`srf08.h`):
 
```c
#define SRF08_DEFAULT_ADDR        0xE0   // 8-bit HAL addr (7-bit: 0x70)
#define SRF08_RECOMMENDED_GAIN    6      // Low: reduces false echoes from floor/walls
#define SRF08_RECOMMENDED_RANGE   140    // 140 × 43mm ≈ 6m
#define SRF08_CMD_RANGE_CM        0x51   // Trigger ranging in centimetres
```
 
### 3.4 Periodic Reading (ThreadX Task)
 
Actual code from `task_srf08.c` — function `task_srf08_step()`:
 
```c
void task_srf08_step(SystemCtx* ctx)
{
    // 1) Trigger: write 0x51 to register 0x00
    HAL_StatusTypeDef ranging_status = SRF08_StartRanging(&s_srf.hsrf08, ctx);
    // Internally: HAL_I2C_Mem_Write(hi2c, 0xE0, SRF08_REG_COMMAND, 1, &cmd_0x51, 1, 100)
 
    // 2) Wait for measurement to complete — fixed sleep 70 ticks (≈ 70ms)
    //    NOTE: SRF08_DISABLE_POLLING = 1 (sensor doesn't support CMD register polling)
    //    Use tx_thread_sleep(), NEVER HAL_Delay() — it blocks the ThreadX scheduler
    tx_thread_sleep(70);  // SRF08_MEAS_WAIT_TICKS
 
    // 3) Read distance: registers 0x02 and 0x03 (big-endian on sensor, 2 bytes)
    uint16_t distance_cm = SRF08_GetDistanceCm(&s_srf.hsrf08, ctx);
    // Internally: HAL_I2C_Mem_Read(hi2c, 0xE0, SRF08_REG_RANGE_H, 1, data, 2, 100)
    // Returns: (data[0] << 8) | data[1]
 
    // 4) Read ambient light: register 0x01
    uint8_t light = SRF08_GetLight(&s_srf.hsrf08, ctx);
    // Internally: HAL_I2C_Mem_Read(hi2c, 0xE0, SRF08_REG_LIGHT, 1, &light, 1, 100)
 
    // 5) Convert cm → mm (CAN frame unit)
    uint16_t distance_mm_raw = (distance_cm == 0xFFFF) ? 0 : (uint16_t)(distance_cm * 10u);
 
    // 6) Median filter (3 samples, insertion sort) — rejects spikes
    uint16_t distance_mm = srf08_apply_filter(distance_mm_raw, light);
 
    // 7) Send CAN frame 0x423 (SRF08Distance_t, 8 bytes)
    //    Conditional: only sends when light > 0 (confirms sensor actually read something)
    if (light > 0) {
        SRF08Distance_t srf08_frame;
        srf08_frame.distance_mm   = distance_mm;   // uint16, mm
        srf08_frame.light_level   = light;          // uint8, raw 0-255
        srf08_frame.gain          = 0;              // not populated
        srf08_frame.range_setting = 0;              // not populated
        srf08_frame.reserved[0]   = 0;
        srf08_frame.reserved[1]   = 0;
        srf08_frame.status        = 0x01;           // bit 0: valid reading
 
        mcp_send_message(CAN_ID_SRF08_DISTANCE,    // 0x423
                         (uint8_t*)&srf08_frame,
                         sizeof(srf08_frame));      // 8 bytes
    }
 
    // 8) Update shared state (for AEB task to read)
    tx_mutex_get(&ctx->state_mutex, TX_WAIT_FOREVER);
    ctx->state.srf08_distance_mm = distance_mm;
    ctx->state.srf08_light       = light;
    ctx->state.srf08_ts          = tx_time_get();
    ctx->state.srf08_valid       = (distance_cm != 0xFFFF) ? 1 : 0;
    tx_mutex_put(&ctx->state_mutex);
 
    // Effective frequency: ~14 Hz (limited by 70ms measurement time)
    // No additional sleep — loop resumes immediately after read
}
```
 
Thread info (`thread_config.h`):
- Priority: 11 (`SRF08_THREAD_PRIORITY`) — same priority as CAN_RX (safety-critical)
- Stack: 2048 bytes
- Scheduling: `TX_NO_TIME_SLICE` (FIFO within the same priority)
 
### 3.5 Lessons Learned
 
- **Ranging time:** The SRF08 needs ~65ms. If you read before that, you get the previous value. Use `tx_thread_sleep(70)`, never `HAL_Delay()` (blocks the ThreadX scheduler).
- **Polling disabled:** The SRF08 in this project doesn't support CMD register polling (stays at 0x0B instead of returning 0x00 when finished). `SRF08_DISABLE_POLLING = 1` uses a fixed sleep instead.
- **I2C address:** The ST HAL uses 8-bit addresses → always `0xE0` in code, not `0x70`.
- **CAN unit:** The CAN frame sends in mm, not cm. `distance_mm = distance_cm * 10`.
- **Median filter:** 3 samples (insertion sort). Latency: ~214ms to stabilize. Rejects spikes better than a simple average.
- **Mutex is mandatory:** All I2C1 accesses take `ctx->i2c1_mutex` — other tasks (Battery, MotorDriver) share the same bus.
- **AEB is not the SRF08 task's responsibility:** `task_aeb.c` reads `ctx->state.srf08_distance_mm` and decides autonomously about braking. The SRF08 task only provides data.

## 4. STM32 → CAN TX — Packing and Sending
 
### 4.1 CAN Frame Structure
 
Each CAN frame has:
- **CAN ID** (11 bits standard, SFF) — identifies the message type
- **DLC** (0-8 bytes) — data length
- **Data** (up to 8 bytes) — values packed into a C struct with `__attribute__((packed))`
 
#### SRF08 CAN ID in the project
 
```c
// can_id.h
#define CAN_ID_SRF08_DISTANCE   0x423
 
// Frame: SRF08Distance_t (8 bytes, packed, little-endian)
typedef struct __attribute__((packed)) {
    uint16_t distance_mm;    // Bytes 0-1: distance in mm (0–6000)
    uint8_t  light_level;    // Byte  2:   ambient light (0–255, raw)
    uint8_t  gain;           // Byte  3:   active gain (0 = not populated)
    uint8_t  range_setting;  // Byte  4:   active range (0 = not populated)
    uint8_t  reserved[2];    // Bytes 5-6: reserved
    uint8_t  status;         // Byte  7:   bit0=valid, bit1=init_error
} SRF08Distance_t;
 
// DLC = 8 bytes
// Encoding: little-endian (Cortex-M, packed struct)
// Send condition: only when light_level > 0
```
 
### 4.2 Why This Encoding
 
- **Millimetres:** Higher precision than cm, no scaling needed — direct integer.
- **Little-endian:** Natural convention for Cortex-M33 with packed structs. Different from some automotive CAN conventions (big-endian) — watch out when unpacking on the RPi5.
- **8 bytes (full frame):** `sizeof(SRF08Distance_t) = 8` — fills the maximum DLC.
- **Light included:** Free from register 0x01, included in byte 2.
- **Status byte:** Allows the receiver to know if the reading is valid without a sentinel value.
 
### 4.3 Send Code (mcp_send_message)
 
All CAN transmission goes through `mcp_send_message()` in `can_tx.c`:
 
```c
void mcp_send_message(uint16_t id, uint8_t *data, uint8_t len)
{
    uint8_t buf[6 + 8];
 
    // MCP2515 header: Load TX Buffer command (0x40)
    buf[0] = MCP_LOAD_TX;               // 0x40
    buf[1] = (id >> 3) & 0xFF;          // SIDH: bits [10:3] of CAN ID
    buf[2] = (id & 0x07) << 5;          // SIDL: bits [2:0] in bits [7:5]
    buf[3] = 0x00;                      // EID8 (extended ID, not used)
    buf[4] = 0x00;                      // EID0 (extended ID, not used)
    buf[5] = len & 0x0F;                // DLC
 
    for (uint8_t i = 0; i < len; i++)
        buf[6 + i] = data[i];
 
    // Send via SPI1 with mutex
    tx_mutex_get(&ctx->spi1_mutex, TX_WAIT_FOREVER);
 
    MCP_CS_L();                                           // CS LOW
    HAL_SPI_Transmit(&hspi1, buf, 6 + len, HAL_MAX_DELAY);
    MCP_CS_H();                                           // CS HIGH
 
    uint8_t cmd = MCP_RTS_TXB0;                          // 0x81: Request To Send
    MCP_CS_L();
    HAL_SPI_Transmit(&hspi1, &cmd, 1, HAL_MAX_DELAY);
    MCP_CS_H();
 
    tx_mutex_put(&ctx->spi1_mutex);
}
```

## 5. RPi5 CAN RX → VSS Bridge — Receiving and Translating
 
> **Status:** This layer is not yet implemented in this codebase (March 2026).
> What currently exists are direct Python scripts (python-can) for testing and manual control.
> This section describes the planned architecture.
 
### 5.1 What the CAN-VSS Bridge Will Be
 
The bridge will be a Python script on the RPi5 (AGL) translating between:
- **CAN** (binary frames with numeric IDs, little-endian)
- **VSS** (Vehicle Signal Specification, readable paths → Kuksa databroker)
 
```
CAN Frame (0x423, 8 bytes LE)
    b[0..1]: 0x2D 0x01 → distance_mm = 0x012D = 301 mm
    b[2]:    0x8A      → light_level = 138
    │
    │ struct.unpack_from('<H', data, 0)  ← little-endian uint16
    ▼
    distance_mm = 301
    │
    │ kuksa-client gRPC
    ▼
Kuksa.val: Vehicle.ADAS.ObstacleDetection.DistanceFront = 0.301  (metres)
```
 
> ⚠️ **Watch the endianness:** CAN frames in this project are little-endian (C structs from
> Cortex-M). Use `struct.unpack_from('<H', ...)` in Python (not `>H`).
 
### 5.2 SocketCAN Configuration on AGL

### 5.3 Bridge Structure (to be implemented)
 
```python
import can
import struct
 
# CAN ID → unpacking function mapping
# NOTE: little-endian ('<' in struct)
 
def unpack_srf08(data):
    distance_mm, light = struct.unpack_from('<HB', data, 0)
    return {
        'Vehicle.ADAS.ObstacleDetection.DistanceFront': distance_mm / 1000.0,  # metres
        'Vehicle.ADAS.ObstacleDetection.AmbientLight': light,
    }
 
def unpack_wheel_speed(data):
    rpm, total_pulses, direction, status = struct.unpack_from('<iIBB', data, 0)
    speed_kmh = abs(rpm) * (66.75e-3 * 3.14159) * 60 / 1000  # approx.
    return {
        'Vehicle.Speed': speed_kmh,
        'Vehicle.Powertrain.Transmission.CurrentGear': direction,
    }
 
def unpack_battery(data):
    voltage_mv, current_ma, soc = struct.unpack_from('<Hhb', data, 0)
    return {
        'Vehicle.Powertrain.Battery.Voltage': voltage_mv / 1000.0,
        'Vehicle.Powertrain.Battery.CurrentCurrent': current_ma / 1000.0,
        'Vehicle.Powertrain.Battery.StateOfCharge.Current': soc,
    }
 
CAN_HANDLERS = {
    0x423: unpack_srf08,
    0x403: unpack_wheel_speed,
    0x421: unpack_battery,
    # ... add the rest
}
 
bus = can.interface.Bus(channel='can0', bustype='socketcan')
 
for msg in bus:
    handler = CAN_HANDLERS.get(msg.arbitration_id)
    if handler:
        values = handler(msg.data)
        # publish values to Kuksa via gRPC
        # client.set(path, value)
```

## 7. Recipe — Adding a New Sensor
 
Checklist for integrating any new sensor into the system:
 
**Hardware:**
- [ ] Connect the sensor to the STM32 (I2C1 for external sensors; I2C2 for onboard)
- [ ] Confirm power supply (3.3V vs 5V) and pull-ups
 
**STM32:**
- [ ] Configure peripheral in CubeMX if needed (already generated for I2C1 and I2C2)
- [ ] Confirm detection: `HAL_I2C_IsDeviceReady()` with `ctx->i2c1_mutex`
- [ ] Write driver: `sensor_init()` + `sensor_read()` (`HAL_I2C_Mem_Write/Read`)
- [ ] Create ThreadX task in `Core/Src/tasks/task_<sensor>.c`
- [ ] Set priority in `thread_config.h`
- [ ] Never use `HAL_Delay()` in tasks — use `tx_thread_sleep()`
- [ ] Register thread in `app_threadx.c` (`App_ThreadX_Init`)
 
**CAN:**
- [ ] Choose CAN ID (see table in section 4.4, respect priorities; max 0x7FF)
- [ ] Add `#define CAN_ID_<SENSOR> 0xXXX` in `can_id.h`
- [ ] Define `__attribute__((packed))` struct for the frame (always little-endian)
- [ ] Send with `mcp_send_message(CAN_ID_<SENSOR>, (uint8_t*)&frame, sizeof(frame))`
 
**RPi5 / AGL:**
- [ ] Verify reception: `candump can0 | grep <CAN_ID_hex>`
- [ ] Add handler in CAN-VSS bridge (unpack with `struct.unpack_from('<...', data, 0)`)
- [ ] Note: little-endian (`'<'` in struct format, not `'>'`)
 
**Kuksa (when implemented):**
- [ ] Choose VSS path (follow COVESA VSS standard)
- [ ] Publish to Kuksa (`client.set()`)
- [ ] Test end-to-end — value in Kuksa CLI matches real measurement
 
**Documentation:**
- [ ] Update CAN ID table (section 4.4)
- [ ] Update VSS mapping (section 5.4)
- [ ] Update thread table if new task created
